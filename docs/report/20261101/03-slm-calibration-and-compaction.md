# 03 — SLM Dynamics, Calibration, and Frequent Intentional Compaction

## 1. The Hardware Reality: Modernization on 27B Parameter Models

A critical divergence between academic multi-agent literature and production systems engineering lies in compute assumptions. Many contemporary frameworks (such as ReCodeAgent) evaluate primarily against frontier proprietary models (e.g., Claude 3.5 Sonnet, GPT-4o) possessing massive context windows ($128\text{k}$–$200\text{k}$ tokens) and multi-datacenter compute clusters.

While frontier models can temporarily mask architectural inefficiency by ingesting entire codebases and thousands of lines of compiler logs in a single prompt, this creates two severe vulnerabilities:
1. **Cost & Latency Barrier**: Running hundreds of iterative rollouts over $50\text{k}$+ token prompts on commercial APIs incurs prohibitive monetary costs ($>\$50$ per small library) and high network latency.
2. **Obscured Architectural Flaws**: Relying on brute-force context windows hides architectural pathologies—such as missing backward topological recovery, lack of pre-DAG invariant mining, and cascading diagnostic noise.

### The werðan Hardware Constraint

The **werðan** (THESEUS) engine is designed and calibrated for **local, private, on-premise inference** running on commodity workstation hardware:
* **Host Platform**: Linux x86_64 (`7.3.0-cachyos`).
* **Accelerator**: Single NVIDIA GeForce RTX 3090 (24 GB GDDR6X VRAM).
* **Serving Stack**: Local continuous-batching inference daemon (`ninfer`, port 8092).
* **Model**: `swift-1.5-qwen3.8-27b` (27 billion parameter dense Small Language Model).

Operating a 27B model on a single 24 GB GPU mandates strict context efficiency and exact mathematical parameter calibration.

## 2. The "Smart Zone" vs. "Dumb Zone" Phenomenon

Through extensive empirical monitoring of thousands of LLM inference requests across the CRUST dataset, we observed a pronounced non-linear behavioral phase shift governed by prompt token depth:

```
 Token Depth:   0k ─────── 8k ─────── 12k ─────── 16k ─────── 24k+
                [   THE SMART ZONE   ]  [  TRANSITION  ]  [   THE DUMB ZONE   ]
 Reasoning:     High-fidelity AST      Borderline         Severe degradation:
                Borrow-checker safe    Syntax drift       Repetition loops,
                Precise error repair   Missed hints       Hallucinated ABIs
```

### 1. The Smart Zone ($\le 12\text{k}$ tokens)
When prompt payloads are maintained strictly at or below $12\text{k}$ tokens:
* The 27B SLM exhibits sharp syntactic adherence to Rust 2024 edition idioms.
* It correctly reasons about borrow-checker lifetimes (`&'a`, `&mut`), slice indexing, and ownership transfer.
* It accurately localizes diff repairs based on compiler diagnostic lines without modifying surrounding signatures.

### 2. The Dumb Zone ($> 12\text{k}$ tokens)
Once accumulated context exceeds $12\text{k}$ tokens (approaching $16\text{k}$–$24\text{k}$):
* **Instruction Hierarchy Loss**: The model ignores system role directives and begins echoing input snippets verbatim or emitting conversational filler (`"Sure! Here is the updated code..."`).
* **Repetitive Oscillation**: Faced with borrow-checker errors, the model enters cyclic thrashing (e.g., adding `&mut` on iteration $t$, removing it on iteration $t+1$, re-adding it on iteration $t+2$).
* **Signature Drift**: It alters exported function names or argument types, inadvertently breaking external integration test harnesses.

**Design Invariant**: An effective SLM modernization engine must guarantee that prompt payloads stay strictly within the Smart Zone ($\le 12\text{k}$ tokens) throughout all phases.

## 3. ARIADNE Search Constant Calibration ([ADR-0012](../../decisions/0012-ariadne-constant-calibration.md))

The formal theoretical derivation in `docs/references/METHODOLOGY.md` specifies Softmax-UCB temperature $\tau = 0.35$ and gamma prior weight $\gamma = 0.15$. However, running these values against a local 27B SLM revealed a critical failure mode: **premature greedy collapse**.

### The Failure of Theoretical $\tau = 0.35$ on SLMs

In Monte Carlo Tree Search, child node selection follows:

$$\text{UCB}(u) = \bar{R}(u) + C_{\text{exp}} \sqrt{\frac{\ln(N(v) + 1)}{N(u)}} + \gamma \cdot P_{\text{prior}}(u)$$

$$p(u \mid v) = \frac{\exp\big((\text{UCB}(u) - \max_w \text{UCB}(w)) / \tau\big)}{\sum_{w \in \text{Children}(v)} \exp\big((\text{UCB}(w) - \max_{w'} \text{UCB}(w')) / \tau\big)}$$

With $\tau = 0.35$, the probability distribution over child nodes is extremely steep:
* If the first strategy hypothesis $h_1$ generated by $\mathcal{A}_{\text{str}}$ achieves a partial compilation reward (e.g., $R = 0.20$), its UCB score jumps relative to unvisited siblings ($N(u)=0$).
* At $\tau = 0.35$, the controller samples $h_1$ with $> 85\%$ probability on subsequent rollouts.
* If $h_1$ is an architectural dead-end (e.g., replicating C pointer manipulation via raw pointers `*mut T` rather than safe slices), the search repeatedly forces $\mathcal{A}_{\text{patch}}$ to repair an inherently unfixable candidate, burning the entire rollout budget $B_{\max}$ without ever testing alternative hypothesis $h_2$.

### Calibrated In-Tree Constants

To resolve this, [ADR-0012](../../decisions/0012-ariadne-constant-calibration.md) established calibrated in-tree defaults in `werðan/libs/holon/engine/src/types.rs` (`EngineConfig::default()`):

| Constant | `METHODOLOGY.md` (Theory) | In-Tree Calibrated (ADR-0012) | Operational Justification for 27B SLM |
|:---|:---:|:---:|:---|
| **Softmax Temperature ($\tau$)** | $0.35$ | **$0.50$** | Higher entropy prevents greedy entrapment on flawed initial templates, forcing balanced exploration of distinct strategies. |
| **Gamma Prior Weight ($\gamma$)** | $0.15$ | **$0.50$** | Empowers high-confidence strategy priors from $\mathcal{A}_{\text{str}}$ to compete against early noisy partial rewards. |
| **UCB Exploration Constant ($C_{\text{exp}}$)** | $1.414$ ($\sqrt{2}$) | **$1.414$** ($\sqrt{2}$) | Retains the canonical theoretical balance between exploitation and exploration visit counts. |
| **Generative Temperature** | $0.20$ | **$0.20$** | Low temperature guarantees deterministic, high-precision code synthesis from $\mathcal{A}_{\text{gen}}$ and $\mathcal{A}_{\text{patch}}$. |
| **Reward Weights ($w_{\text{comp}} / w_{\text{char}} / w_{\text{hard}}$)** | $0.20 / 0.60 / 0.20$ | **$0.20 / 0.60 / 0.20$** | Gated sum ensures compilation is a strict prerequisite; characterization test parity dominates reward. |
| **Rollout Budget ($B_{\max}$)** | Config-dependent | **$16$** (LoC Tier 1) | Calibrated for 27B throughput, providing sufficient depth without GPU thermal throttling. |

## 4. Frequent Intentional Compaction ([ADR-0018](../../decisions/0018-frequent-intentional-compaction.md))

When a candidate target program fails compilation or testing, the deterministic execution harness ($\mathcal{A}_{\text{eval}}^{\text{exec}}$) captures raw output from `rustc` and `cargo test`.

In systems programming, a single type mismatch or missing trait implementation frequently triggers **cascading compiler vomit**:
* 5 to 20 secondary errors caused entirely by the first error.
* Verbose stack traces, type expansion diffs, and multiple lines of `help:` suggestions.
* Dumps of unformatted standard library source paths.

Passing raw compiler traces into the repair prompt instantly blows past the $12\text{k}$ token threshold into the Dumb Zone.

### The Three-Stage Compaction Pipeline

Under [ADR-0018](../../decisions/0018-frequent-intentional-compaction.md), werðan enforces **Frequent Intentional Compaction** via `compact_diagnostic_trace` in `werðan/libs/holon/agents/holon-patch/src/lib.rs`:

```
 [Raw rustc / cargo test Diagnostic Trace: 5,000 - 15,000 chars]
                            │
                            ▼
 1. Semantic Marker Filter:
    - Retain only lines matching: error[E..., warning, -->, :::, or numbered lines (  12 |)
    - Drop verbose compiler notes, macro expansions, and trailing warnings
                            │
                            ▼
 2. Primary Error Capping:
    - Filter to top-3 primary compiler errors (drops cascading phantom errors)
                            │
                            ▼
 3. Character Budget Clamp:
    - Hard clamp: trace.chars().take(2048)
                            │
                            ▼
 [Compacted Diagnostic Payload: ≤ 2,048 chars (~500 tokens)]
```

### Empirical Impact on Context Payloads

In our benchmark runs on `crust.libwecan`, raw compiler traces for bitfield packing ranged from $4,800$ to $12,200$ characters. Under ADR-0018 compaction:
* Diagnostic payloads are compressed by **70%–85%**, strictly capped at $\le 2,048$ characters.
* Total prompt context delivered to $\mathcal{A}_{\text{patch}}$ (including system prompt, Problem Model, candidate code, and fault trace) peaked at **7,420 tokens**.
* This guaranteed that 100% of the 78 inference calls on `libwecan` executed squarely within the high-fidelity Smart Zone ($\le 12\text{k}$ tokens).

## 5. Algorithmic Guardrails: Stagnation Braking & Partial Candidate Promotion

Even with temperature calibration and compaction, search trajectories can occasionally plateau if the model lacks the semantic capability to solve a specific algorithmic invariant.

To prevent infinite loops and wasted GPU cycles, werðan incorporates two runtime guardrails:

### 1. MCTS Stagnation Early Termination
In `werðan/libs/holon/engine/src/controller.rs`, the MCTS controller maintains a rolling window of recent rollout rewards. If the search records **8 consecutive flat rollouts** (zero reward improvement across rollouts $t \dots t+8$), the stagnation brake triggers:
* The rollout loop terminates early without exhausting the full $B_{\max} = 16$ or $64$ budget.
* The module is safely parked, preventing GPU thermal throttling and saving up to $75\%$ of inference time.

### 2. Candidate Promotion on Budget Exhaustion
In `METHODOLOGY.md` Algorithm 2 (line 338), budget exhaustion without $R = 1.0$ dictates broadcasting $\texttt{ev\_ContractConflict}$ to the parent. However, in single-module or leaf projects where no parent exists to negotiate contracts, this would force an unrecoverable failure.

In `global-engine`, werðan introduces candidate promotion on budget exhaustion:
* If the highest-reward candidate achieves $R(u_{\text{best}}) \ge 0.50$ (indicating that the code compiles cleanly and passes partial characterization tests), the candidate is **promoted to hardened status**.
* This allows compilable, high-utility code to be preserved as a deliverable target rather than discarded.

## 6. Companion Header Self-Contracts ($\mathcal{C}(v_i, v_i)$)

In C codebases, a source file `module.c` is accompanied by a public interface header `module.h`. Integration test binaries link against `module.h`, expecting exact function signatures and type definitions.

If an LLM translator translates `module.c` in isolation:
* It often "modernizes" free function signatures into idiomatic object-oriented struct methods (e.g., converting `rhbloom_add(filter, key)` into `RHBloom::add(&mut self, key)`).
* While object-oriented Rust is idiomatic, integration test binaries in the benchmark harness still call the C-style free functions!
* The translated library compiles in isolation, but all integration binaries immediately crash with `E0425: cannot find function in this scope`.

### Seeding Self-Contracts in `bench_harness.rs`

To resolve this signature disconnect, werðan automatically parses companion headers `include/{stem}.h` during blackboard initialization:
* It synthesizes **Self-Contracts $\mathcal{C}(v_i, v_i)$** stored directly in the Problem Model's `export_obligations`.
* Prompts delivered to $\mathcal{A}_{\text{gen}}$ and $\mathcal{A}_{\text{patch}}$ explicitly mandate that the generated Rust crate MUST expose the exact public free functions and struct definitions defined in the companion header.
* This guarantees that synthesized target crates maintain 100% ABI and symbol compatibility with existing integration test suites.
